# v2.0.1 core storage and algorithm qualification

The v2.0.1 objective is a backwards-compatible, framework-independent geography engine. "Complete" for these two workstreams means all contracts and measured budgets below pass. It does **not** claim that future optimization is mathematically impossible or guarantee one-nanosecond queries on every PHP deployment.

## Storage architecture

1. The bundled JSON sources remain the canonical, inspectable data records. Their historical source-local identifiers must not be mistaken for present-day official government identifiers.
2. Validate every source row, native integer ID and parent reference before accepting a snapshot. Reject duplicate identities, orphaned records and invalid or missing files.
3. Hydrate bottom-up one source level at a time, reusing the same model instances in nested hierarchy collections.
4. Avoid redundant array allocations when validating decoded lists and flattening nested collections. Offer `iterate(level)` for streaming instead of allocating all descendants.
5. Bound ancestry caching to 512 distinct identities and scoped exact-name results to 256 queries. Do not cache arbitrarily large same-name result sets.
6. Preserve the existing PHP 8.2+ API, nested `toArray()` semantics and no-runtime-service installation model. No compulsory SQLite, Redis, database migrations or native search extensions.

The evaluated default is the immutable in-memory model tree with per-level lazy indexes. A separate packed format, SQLite store or `SplFixedArray` may be useful for different deployment requirements but is not automatically superior for the current sparse-ID dataset and public object API. PHP's official documentation describes generators as a way to avoid prebuilding collections and `array_values()` as reindexing an existing array. Both properties informed the selected streaming and eager-list paths.

References: https://www.php.net/manual/en/language.generators.overview.php and https://www.php.net/manual/en/function.array-values.php

## Lookup algorithms and complexity

| Operation | Candidate strategy | Expected warm complexity |
| --- | --- | --- |
| Exact ID | Native associative index built per requested level | Average O(1) |
| Global exact name | Normalized hash index preserving all duplicate IDs | Average O(1 + matches) |
| Parent-scoped exact name | Resolve parent's existing children and memoize bounded query results | Cache hit O(1 + matches), miss O(children) |
| Global prefix | Lazy lexicographically sorted normalized keys and binary search | O(log unique_names + candidates) |
| Parent-scoped prefix | Sort matching child name groups without building a global index | O(children + matching_names log matching_names) |
| Direct children | Read canonical parent's child list | O(children returned) |
| Ancestors | Follow at most four parent links with a bounded ring cache | O(level_depth) uncached, O(1) cache hit |
| Full collections | Direct nested traversal into one output array | O(records returned), output allocation only |
| Streaming | Yield canonical objects without flattening | O(records yielded), constant auxiliary iteration memory |

All source identities and duplicate display names must survive every optimization. Unicode-aware fuzzy matching is a separate v2.0.1 workstream and should not be silently folded into ASCII-compatible exact lookup behavior.

## Reproducible acceptance evidence

The `core-comparison.yml` workflow independently loads the exact `main` and candidate revisions into PHP 8.4 processes on the same GitHub runner. Its 16 scenarios cover IDs, names, children, ancestry and array collection traversal at every nesting level.

It compares ordered model type/ID fingerprints and every administrative source ID, display name and parent association. The latter is checked through `full-hierarchy-fingerprint.php`, making silent data loss a release blocker.

For each scenario the workflow retains constructor time, first query latency, batched warm p50/p95/p99, warm mean and process peak memory. The `verify-relative-budgets.php` guard rejects a changed identity, a significant cold/warm regression or excess allocation. Thresholds include stated noise allowances because hosted microbenchmarks are not deterministic.

Successful `PHPUnit`, `PHPStan`, source integrity, isolated Composer consumer, release and performance workflows are necessary. Passing a performance budget never substitutes for correctness or manual architectural review.

## Remaining release-wide gates outside these phases

Advanced Unicode normalization, fuzzy search, broader property-based testing and the final independent PR audit are tracked separately. Laravel integration remains excluded from v2.0.1.
