# Standalone PHP integration

All integration operations are opt-in and operate on a selected canonical snapshot. The default source is the bundled historical package snapshot, not a certified up-to-date government register.

## First use

1. Install Composer dependencies in a checkout or consume `kusaasira/uganda-geo` as a library.
2. Export read-only data with `php tools/sync/uganda-geo.php export --format=json --output=/tmp/uganda-geo.json`.
3. Set `UGANDA_GEO_DSN`, `UGANDA_GEO_DB_USER` and `UGANDA_GEO_DB_PASSWORD` as environment variables for commands that need a connection. Credentials must not be placed in CLI arguments or committed configuration.
4. Run `php tools/sync/uganda-geo.php discover` to inspect candidate geography tables without reading application row content.
5. For a standalone managed dataset, explicitly invoke `php tools/sync/uganda-geo.php install`. This creates dedicated Uganda Geo tables but does not import data.
6. Generate `php tools/sync/uganda-geo.php plan --output=plan.json`. Examine conflicts, unmapped identities and the plan hash.
7. If satisfactory, run `php tools/sync/uganda-geo.php apply --plan=plan.json --approve=THE_EXACT_PLAN_HASH`.

`export` supports JSON, NDJSON and CSV. JSON is the faithful interchange format. CSV escapes spreadsheet-formula-leading names by prefixing an apostrophe; it is for safe human-readable import, not byte-exact round trips. Output creation refuses existing files.

## Mapping an existing database

Provide `--mapping=mapping.json` with a checked-in, reviewed mapping definition. An existing mapping may use a custom table and primary key:

```json
{
  "strategy": "existing",
  "levels": {
    "district": {
      "table": "geo_districts",
      "key": "uuid",
      "name": "district_name",
      "write_name": true
    }
  }
}
```

This package does not guess an external application's primary keys. A reviewer explicitly approves one row by running `approve-map --mapping=mapping.json --source=legacy:district:98 --level=district --target=EXISTING_UUID --reviewer=developer-id`. For mapped rows the planner evaluates data differences and explicitly permitted columns. Unmapped records remain unresolved. There are no automatic local primary key insertions or deletions.

By default an existing-schema plan cannot be applied until its source mapping is complete for all selected source records. A developer may explicitly set `unmapped_policy: ignore` in the mapping JSON to synchronize only reviewed matches while reporting all unmapped source records. A narrower mapping level can be configured while the remaining levels are omitted.

## Production notes

- The CLI executes synchronously. Operate it under an external scheduler or job supervisor if asynchronous processing is required.
- The executor owns one transaction for its entire plan and applies changes only after validating the exact plan hash against current target rows. Size and timeout limits should be tested before choosing to run a large snapshot.
- For a production environment, pin snapshots, use narrowly privileged credentials, take backups, rehearse a dry run and verify restoration.
- Data exported from third-party sources remains governed by source-specific rights and attribution.

## Laravel queued execution

A Laravel consumer can run `php artisan uganda-geo:sync --plan=approved.json --approve=PLAN_HASH --queue`. The command stores the approved plan and selected canonical snapshot on the private disk specified by `UGANDA_GEO_SYNC_STORAGE_DISK`, then queues a job that validates the pinned artifacts and the exact mapping scope again before applying. Configure a disk shared by every worker in a distributed deployment and ensure that the queue worker has the correct application configuration. The database operation is one transaction: failed jobs roll back and retry from the beginning, not from an uncommitted mid-run checkpoint. A transaction timeout or platform size limit requires operational tuning. Job retries do not constitute a multi-batch resumable migration.
