# Schema-aware integration and verified identity contracts

Uganda Geo's source-local numeric identifiers are not certified current government codes. Administrative names are not unique. A similarity score never authorizes a write.

## Opt-in database setup

The `SchemaInstaller` creates dedicated metadata tables only after an explicit call. Installing Composer packages, resolving services, creating an object or running discovery MUST NOT execute database DDL or DML. Schema installation must happen outside transaction boundaries because supported database engines differ in transactional DDL semantics.

## Managed and external schemas

Managed mode mirrors validated canonical records into `uganda_geo_units` with SHA-256 source identity hashes. Existing mode never replaces host primary keys. Hybrid mode mirrors into dedicated tables while supporting separately approved external crosswalks.

External mappings specify exact table, primary key, label and optional foreign-key column. The application owns all unspecified columns. Source-to-target keys live in `uganda_geo_identity_maps` with an explicit scope and reviewer. Mapping suggestions are only suggestions. Registering an approved mapping requires an exact existing target record.

## Security invariants

- Identifiers are validated before interpolation and values use prepared PDO parameters.
- No writable action is triggered by read-only discovery or dry-run planning.
- No fuzzy match, unverified numeric code or identical name can approve a target mapping.
- SQL writes must be guarded by exact plan approval and re-validation.
- Never automatically delete, retire or reparent unmatched host records.
- Applications should grant read-only DB credentials for schema discovery and plan preview.
- Always segregate tenant or organization mappings using the explicit mapping scope. A scope is not a substitute for an application-level permission check.
- Production operators should review SQL privileges, backup policies and restore procedures before enabling writes.

## Tenant-scoped target tables

For shared multitenant target tables, add `scope_column` to the level mapping and configure a target-specific `scope` matching the stored tenant key. Reviewed identity lookups, planner reads and guarded updates all include that scope predicate. The target primary key must still have a verified single-column unique constraint. Applications with compound tenant-local identifiers should use the managed or hybrid strategy until a reviewed composite-key adapter is available. The library cannot authenticate a tenant by itself; the calling application must authorize the selected connection, scope and approval operation.

## Existing Laravel model behavior

Existing-table synchronization uses prepared PDO statements and **does not run Eloquent model lifecycle events, model casts, global scopes, observers or application-specific validation**. Developers must explicitly decide whether writing named columns directly is compatible with their domain rules. For schemas where application events or projections are authoritative, use managed or hybrid mode and let the application perform its own reviewed projection into domain models.

An external mapping's primary key must be globally unique under the verified table constraint. Tenant-scoped predicates restrict approval, reads and updates, but do not replace a consuming application's authentication, authorization or row-level security policies.

## Queue worker and retention requirements

Laravel queue artifacts include local target identifiers and mapping reports. Store them on a private disk with access controls and a defined retention policy. All distributed workers must share the configured source/plan storage disk and database connection. The job timeout is 900 seconds, so the queue connection's retry-after setting must exceed that timeout and the worker supervisor must allow sufficient termination grace. Configure a durable queue backend, observe failed jobs and verify the selected mapping scope before dispatch. A checkpoint commits only after the corresponding data writes succeed; committed earlier batches are not rolled back when a later batch fails.
